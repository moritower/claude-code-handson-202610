# 02. フェーズ1: 要件・設計 ★重点（0:50–1:30 / 40分）

このパートのゴール:

> 頭の中のふわっとした要望を、Claude Code と対話して
> **仕様書（SPEC）**と**設計メモ（DESIGN）**という“読める形”に変換する。

コードはまだ書きません。**「何を・どう作るか」を言葉にする**練習です。

---

## Step 1. 要望を洗い出す（8分）

まず、追加したい機能を"雑に"Claude Code へ伝えます。
完璧じゃなくてOK。むしろ抜け漏れを見つけてもらいます。

Claude Code に、次のように打ってみましょう。

```
マーダーミステリー公演の予約システムに「予約のキャンセル機能」を
追加したい。まだ仕様は固まっていない。
どんなことを決めておく必要がある? 質問を5つ、箇条書きで挙げて。
```

すると「キャンセル期限は?」「満席待ちの人へ繰り上げる?」など、
**自分では気づかなかった論点**が出てきます。

> 💡 これが AI と要件を詰める第一歩。「答えを出させる」のではなく
> **「問いを出させる」**のがコツです。

### あなたの番

出てきた質問に、自分なりの答えを口頭 or メモで決めてください。例:

- キャンセル期限 → 公演の前日まで
- 繰り上げ → 今回は「なし」（シンプルに）
- キャンセル済みの席 → すぐ残席に戻す

---

## Step 2. 仕様書（SPEC.md）を作らせる（10分）

決めた内容をもとに、仕様書を書いてもらいます。

```
さっきの論点について、次のように決めた:
- 公演前日まではキャンセル可能
- 繰り上げ（キャンセル待ち）は今回は作らない
- キャンセルしたら席はすぐ残席に戻る

この「キャンセル機能」の仕様を docs/SPEC.md にまとめて。
・ユーザーストーリー
・受け入れ条件（箇条書き・テストできる粒度で）
・APIの入出力（エンドポイント / リクエスト / レスポンス）
の3セクションで。コードはまだ書かないで。
```

生成された `sample-app/docs/SPEC.md` を**必ず自分で読みます**。
違和感があれば、そのまま会話で直します。

```
受け入れ条件に「存在しない予約IDを指定したときの動作」も足して。
```

> 🔑 **ポイント**: 仕様書は"AIとの共通の地図"。
> ここが曖昧だと、この後の実装も曖昧になります。

---

## Step 3. Plan モードで設計を相談する（12分）

次は「どう実装するか」の方針＝設計です。
ここでは **Plan モード**（考えるだけで、まだ変更しないモード）を使います。

Claude Code で `Shift+Tab` を数回押し、**Plan mode** にします
（画面に plan と表示されます）。その状態で:

```
SPEC.md のキャンセル機能を、今のコード構成に沿って実装する計画を立てて。
・どのファイルをどう変えるか
・src/booking.js と src/store.js の役割分担をどう保つか
・テストは何を追加するか
まだコードは書かないで、計画だけ見せて。
```

Claude Code が「変更計画」を提示します。ここで:

- 分からない用語があれば「○○ってどういう意味?」と聞く
- 方針が気に入らなければ「store.js には状態変更だけ置きたい」など注文する

納得できる計画になったら、その要点を設計メモに残します。

```
今の計画を docs/DESIGN.md に、決定事項と理由がわかる形で保存して。
```

> 🧭 Plan モードの良さは「**いきなり作られて驚く**」を防げること。
> 設計に集中できます。

---

## Step 4. レビュー観点で見直す（7分）

最後に、少し視点を変えて仕様の穴を探します。

```
このキャンセル機能の仕様と設計について、
初心者がハマりやすい抜け漏れを、レビュアーの視点で指摘して。
（例: 同時に2人がキャンセルしたら? など）
```

出てきた指摘のうち「今回対応する / しない」を決め、
SPEC.md の最後に「今回のスコープ外」として明記してもらいましょう。
